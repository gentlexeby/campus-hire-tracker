# 秋招进度板：产品需求文档（PRD）

> 仓库名：`campus-hire-tracker`
> 当前范围：Windows 本地单用户版本
> 文档状态：已确认，可进入实现
> 本文中的“必须”“应”“可以”含义遵循 [开发文档索引](README.md)；领域命名以 [术语表](GLOSSARY.md) 为准。

## 1. 产品摘要

秋招进度板是一款本地优先的个人求职管理工具。它以“岗位申请”为主线，把申请阶段、唯一的下一步行动、等待复查、面试与笔试日程、招聘会、JD、面经和复盘放入同一套可追溯的数据模型中。

首版首先服务产品作者本人。少量朋友可以从私有 GitHub 仓库克隆代码，在各自电脑上运行独立副本。不同副本之间不共享账号、数据库、附件或提醒。

产品打开后必须优先回答三个问题：

1. 今天和近期有哪些不能遗漏的事项？
2. 每条申请现在处于什么阶段？
3. 每条活跃申请下一步该做什么，或者何时结束等待并复查？

## 2. 背景与问题

秋招信息通常散落在招聘网站、即时通信、邮件、日历、表格和个人笔记中。普通表格适合列出岗位，但难以同时表达多轮面试、日程冲突、资料关联、状态历史和等待后的复查动作；普通日历能提醒时间，却不能说明一条申请的完整上下文和当前责任。

本产品要解决的不是“收集尽可能多的招聘信息”，而是让用户可靠推进自己已经关注或投递的机会，并在求职周期结束后有完整、可搜索、可恢复的个人记录。

## 3. 产品目标

### 3.1 核心目标

- **零遗漏**：已录入的硬截止、面试、笔试和招聘会必须在“今日”与日历中按风险优先级呈现，并可导出到系统日历。
- **状态清楚**：用户能快速看出每条申请的主阶段、优先级、最近事件和历史变化。
- **行动明确**：每条活跃申请必须处于且只处于一种可解释模式：有一个突出显示的下一步行动、带复查日期的等待状态，或显式进入“缺少下一步”风险队列。
- **资料有上下文**：JD、外部面经和个人面试记录与公司、申请或具体面试轮次建立明确关联。
- **数据可掌控**：数据默认只保存在本机，能完整备份、验证和恢复；代码更新不得覆盖个人数据。
- **低摩擦录入**：收到岗位或面试通知后，用户无需填写完整表单即可先建立记录，随后再补充信息。

### 3.2 产品原则

- 用户是申请阶段和事件结果的最终确认者，系统只提醒或建议，不自动推进。
- “下一步行动”不是通用待办清单；每条申请只突出当前最重要的一项。
- AI 是可选的录入助手，不能成为任何核心流程的前置条件。
- 隐私默认开启；不存在未经明确选择的上传、分享或遥测。
- 先保证数据完整、备份和恢复，再扩展便利功能。
- 面向焦虑场景提供克制、确定的反馈，不使用积分、连续打卡或施压式文案。

## 4. 用户与运行模式

### 4.1 产品角色

| 角色 | 描述 | 权限边界 |
| --- | --- | --- |
| 本地用户 | 在自己的 Windows 账户中运行产品、管理自己的求职数据 | 可以使用本地副本内的全部业务能力；没有跨设备或跨用户访问能力 |
| 仓库维护者 | 发布代码、数据库迁移和版本说明的人 | 不通过产品访问用户数据；无远程管理入口 |
| 体验朋友 | 从受邀的私有 GitHub 仓库克隆并运行自己的副本 | 在产品内仍是“本地用户”；与作者的数据完全隔离 |

产品首版没有管理员、团队成员、访客、分享链接访问者等在线角色，也没有登录和权限管理界面。

### 4.2 支持边界

- 正式验证环境为 Windows；应用服务固定使用 `http://127.0.0.1:3210`。
- 界面必须响应式，以支持窄窗口并为未来移动端保留空间；首版不宣称手机完整可用。
- 手机侧的可靠提醒通过导入系统日历实现，不要求手机访问本地应用。
- 代码应避免无必要的 Windows 专属业务实现，但 macOS、Linux 未经验证前不属于支持范围。

## 5. 成功标准

### 5.1 进入实现后的个人验证门槛

同时满足以下条件，才可认为本地核心价值已验证：

1. 连续至少 14 天使用产品管理真实秋招流程。
2. 产品中至少存在 20 条真实岗位申请，并覆盖不少于 4 个主阶段。
3. 对所有已录入事件，没有因产品未呈现、提醒丢失或时间错误而错过的面试、笔试或截止时间。
4. 100% 的非归档申请处于以下三种可解释状态之一：有当前下一步、等待中且有复查日期、明确标记为“缺少下一步”并出现在今日风险队列。
5. 成功完成一次“创建完整备份 → 校验 → 恢复 → 核对关键记录和附件”的演练。
6. 在一台未配置过项目的 Windows 环境完成一次“克隆 → 初始化 → 启动 → 更新 → 恢复备份”验证。

### 5.2 关键体验指标

- 在应用已启动的前提下，只填写公司与岗位的快速创建应能在 15 秒内完成。
- “今日”页面首屏必须在不进入详情页的情况下显示所有逾期项、当天事项和冲突。
- 用户应能在最多 3 次主要交互内，从任意一级页面进入一条申请的详情。
- 看板拖动阶段后必须立即出现可撤销反馈；撤销后当前阶段和时间线均保持可追溯。
- 自动保存的普通字段在本地服务可用时应于停止输入后 1 秒内开始保存；长文本草稿不得因刷新或意外关闭而静默丢失。

这些指标通过本地测试夹具、Playwright 流程测试和用户自测清单验证；首版不为统计这些指标而加入遥测。

## 6. 明确不做

以下内容不属于本地首版；新增前必须重新评估产品边界和架构：

- 账号体系、公开注册、邀请码、多人协作、云数据库或跨设备同步。
- 在线公开分享链接、面经社区、评论、点赞或内容审核。
- 服务端邮件、短信、微信通知，以及依赖常驻远程服务的提醒。
- 自动抓取全国招聘会、招聘网站爬取、浏览器插件、邮箱读取和截图 OCR。
- 根据事件结束自动改变申请阶段，或根据 AI 判断录取概率后自动执行动作。
- 通用多任务项目管理、复杂 Offer 评分、成功率预测和自动岗位推荐。
- 任意类型文件网盘；附件仅支持经过验证的图片和 PDF。
- 以手机为主的完整离线应用、局域网 HTTPS 配置或移动端后台通知承诺。
- 默认使用分析 SDK、崩溃上传或行为遥测。
- 首版即维护 Windows、macOS、Linux 三个平台的安装与验收矩阵。

## 7. 领域模型与强制规则

### 7.1 岗位申请

- 一条岗位申请代表“公司 + 岗位 + 招聘批次”的一次独立求职尝试。
- 公司和岗位为创建时唯一必填字段；招聘批次可以为空。
- 公司、岗位和招聘批次相同只触发重复警告，不构成数据库唯一约束。用户确认后可以继续创建。
- 新建申请默认主阶段为“机会池”，默认优先级为“中”。
- 优先级固定为高、中、低三级；标签为用户自由输入的补充分类。
- 来源可以不填写；“未填写”与“自定义”是不同状态。已填写来源支持官网、招聘平台、内推、招聘会、校园渠道和自定义值，并可保存原始链接。M1 的来源控件隐藏“招聘会”；M2 的招聘会实体可用后才启用该选项。来源为招聘会时必须关联招聘会实体，而非只保存文本。

### 7.2 主阶段与归档

主阶段顺序固定为：

`机会池 → 准备投递 → 已投递 → 测评/笔试 → 面试中 → Offer → 归档`

- 阶段可以向前或向后手动变更，不强制线性推进。
- 只有用户操作可以改变阶段；事件创建、开始、结束或标记完成均不得自动改变阶段。
- 系统可以在事件结束或结果录入后建议更新阶段，但建议必须由用户确认。
- 进入“归档”必须选择拒绝、放弃、撤回或其他原因；选择“其他”时必须填写说明。
- Offer 是活跃阶段，不自动归档。
- 阶段变化必须产生时间线条目。撤销阶段变化时恢复原阶段，并追加“已撤销阶段变更”条目，不删除既有审计事实。
- 归档不取消或删除既有事件；与该申请直接或经面试轮次关联的事件保留为历史事实，但默认退出“今日”和所有提醒查询。恢复为活跃状态后，仍在未来且有效的事件可以重新进入提醒。
- 恢复归档时由用户选择任一非归档阶段；`archived_from_stage` 只作为默认建议，不得锁定恢复目标。恢复后还必须设置下一步、进入等待中或明确接受待补。

### 7.3 下一步、等待与待补状态

每条非归档申请必须处于且只处于一种行动模式：

1. **可行动**：有一个当前下一步行动；标题必填，截止时间可选。
2. **等待中**：没有当前下一步行动；复查事件必填并承载复查日期或时刻，等待对象 `waiting_for` 和说明均可选。
3. **待补**：既无下一步行动，也无有效等待状态。合法来源包括快速创建、不完整导入或旧数据迁移、完成或移除当前行动/等待状态后用户明确选择“稍后补充”，以及从归档恢复时接受待补。待补必须显示为风险并进入“今日 > 缺少下一步”。

设置下一步行动会结束等待状态；进入等待状态会清除当前下一步。完成当前下一步后，用户必须选择新下一步、进入等待中或明确保留为待补。产品不得用自动生成的默认行动掩盖缺失信息。

### 7.4 事件与面试轮次

- 事件类型至少包括面试、测评/笔试、招聘会、投递截止和跟进/复查。
- 带具体时刻的事件必须保存开始时间和时区，结束时间可选；未填写结束时间表示一个时间点。全天截止可以只保存日期。
- 时间重叠与时间点冲突的判定以数据模型中的统一规则为准；命中时显著警告，但不得禁止保存，界面也不得为无结束时间的事件擅自补默认时长。
- M1 的面试事件直接关联岗位申请；M2 引入面试轮次后，新事件可以改为关联具体轮次，并由轮次推导所属申请。已有直接关联申请的面试事件不强制迁移。
- 面试轮次属于岗位申请，可重复添加并自由命名；默认建议一面、二面、HR 面等常见名称。
- 面试轮次可以记录类型、顺序、时间、地点或会议链接、面试官、结果和复盘，并可关联一个事件。
- 面试轮次结果与申请主阶段相互独立；记录“通过”或“未通过”不得自动修改主阶段或归档。
- 取消轮次默认保留其关联事件，并提示用户可以另行取消该事件；不允许把“取消轮次”静默等同于“取消事件”。
- 软删除轮次时，默认在同一事务内把该轮次唯一的 `INTERVIEW` 事件改为直接关联所属申请，保留提醒与历史；用户也可以在确认页明确选择让该事件一同进入回收站。

### 7.5 招聘会

- 招聘会是独立实体，不是某条申请的附属备注。
- 一场招聘会可关联多个公司、目标岗位和岗位申请。
- 招聘会应记录时间、地点、链接、参加状态、现场笔记和会后行动。
- 招聘会目标的“现场状态”使用固定产品文案：`NOT_CONTACTED`“未接触”、`CONTACTED`“已接触”、`FOLLOW_UP_NEEDED`“需跟进”、`NOT_INTERESTED`“不再考虑”。
- 用户可以从招聘会的目标岗位创建申请；新申请保留招聘会来源关联。

### 7.6 资料与附件

- 资料明确分为 JD 快照、外部资料和个人面试记录，三类内容不得混入同一个无结构大文本框。
- 资料可以关联公司、岗位申请或具体面试轮次；至少存在一个业务关联。个人面试记录必须关联具体面试轮次，其所属申请由轮次推导。
- JD 快照正文必填，外部链接失效不影响已保存内容。
- 外部资料标题必填，且来源 URL 与正文至少填写一项；来源名和摘要可选。
- 个人面试记录正文必填并必须关联具体面试轮次。
- 个人面试记录默认视为敏感信息，分享时默认排除。
- 正文使用富文本交互，持久化格式必须可导出为 Markdown 并保持基础结构。
- 附件仅接受通过 MIME 和内容签名检查的图片或 PDF，并复制到产品管理的用户附件目录；不得仅保存原文件路径。
- 附件只能直接归属于资料。面试轮次的图片或 PDF 必须通过关联该轮次的 `INTERVIEW_NOTE` 资料间接关联，不提供轮次到附件的直接关系。

### 7.7 删除、恢复与历史

- 普通“删除”将实体移入回收站并记录删除时间，保留 30 天。
- 回收站内数据默认不出现在主导航页面、搜索结果、统计或提醒中。
- 用户可以在 30 天内恢复；恢复时若关联实体已删除，必须说明处理方式并保持数据一致性。若与现有记录发生同名或重复冲突，必须让用户选择“合并到现有记录”或“使用建议后缀重命名后恢复”，不得静默处理；完成恢复不能被重复名称永久阻断。
- “永久删除”不可恢复，必须进行二次确认并清楚列出影响的附件和关联数据。
- 永久删除只立即作用于当前活动数据；旧 generation 和备份可能仍含历史副本。界面必须分别列出并允许用户确认清理，同时说明清理旧 generation 会失去快速回退能力。
- 自动清理到期项目必须在设置中可见，并在实际删除前提供本地提示；首版可以要求用户确认批量清理，不得静默清除唯一副本。

### 7.8 安全、密钥与数据位置

- 正式数据库、附件、SQLite `CaptureDraft`、备份和日志存放于 `%LOCALAPPDATA%\CampusHireTracker` 下的受控子目录，不得写入 Git 工作树。
- 从 M1 起，固定 origin 的 IndexedDB 仅以 `EditorRecoveryDraft` 保护长文本尚未成功保存的内容；它不是正式数据、不进入完整备份，也不代表支持离线创建或离线编辑。M1 不注册 Service Worker。
- M3 的 `OfflineCaptureDraft` 专用于本地服务断连时的快速创建，重连后由用户确认写入；它同样不属于正式数据且不进入完整备份。`EditorRecoveryDraft`、`OfflineCaptureDraft` 与 SQLite `CaptureDraft` 是三类不同对象，界面、清理和恢复行为不得混用。
- 本地服务固定使用 `http://127.0.0.1:3210`。首版依赖 Windows 用户账户和磁盘保护，不额外设置应用密码。
- AI API Key 必须保存在 Windows 凭据管理器，不进入源码、环境样例、数据库、备份、导出、日志或 Git。
- 产品不包含默认遥测。未来若增加匿名统计，必须由用户明确选择加入。

## 8. 功能需求与验收标准

需求按三个“始终可运行”的里程碑交付。一个里程碑只有在其所有 P0 验收项通过后才能宣布完成。

### 8.1 里程碑 1：核心推进循环

#### FR-M1-01 本地初始化与启动（P0）

产品必须提供适合 Windows 的初始化、启动和安全更新入口；首次初始化创建用户数据目录和数据库，日常启动自动打开浏览器。

验收标准：

- 在满足 Node.js 支持版本的全新 Windows 用户环境中，用户可以通过 `setup.cmd` 完成依赖安装、目录创建和数据库初始化。
- `start.cmd` 只启动固定监听 `127.0.0.1:3210` 的服务，并在就绪后打开同一 origin；重复执行不会启动多个冲突实例，端口被其他程序占用时失败且不改端口。
- 代码仓库中不出现真实数据库、附件、备份、草稿或密钥。
- 初始化失败时保留可读错误信息和重试指引，不留下被误判为成功的半初始化状态。

#### FR-M1-02 首次使用引导（P0）

首次进入必须让用户在“创建第一条申请”“导入现有表格”与“查看示例数据”之间选择。里程碑 1 可以将导入入口标记为即将提供，但不得伪装为可用。

验收标准：

- 首次使用不直接展示没有解释的空白看板。
- 示例数据与真实数据有清楚标记，用户可以一次性删除全部示例而不影响真实数据。
- 完成或跳过引导后可在设置中重新打开引导说明。

#### FR-M1-03 快速创建岗位申请（P0）

任意一级页面均可打开快速创建。首屏只强制公司和岗位，其余字段可展开填写。

验收标准：

- 保存有效的公司和岗位后即创建申请，默认阶段为机会池、优先级为中。
- 缺少公司或岗位时在字段附近显示错误并保留已输入内容。
- 检测到相同公司、岗位和招聘批次时展示已有记录摘要；用户可以取消、打开已有记录或确认继续创建。
- 未设置下一步或等待状态的新记录被明确标记为“缺少下一步”，并出现在今日页面对应分区。

#### FR-M1-04 申请看板与表格（P0）

“申请”页面必须同时提供看板和表格视图，并共享筛选条件。

验收标准：

- 看板按固定主阶段分列，默认隐藏归档列；卡片至少显示公司、岗位、优先级、下一步或等待复查、最近事件。
- 表格至少支持公司、岗位、阶段、优先级、来源、截止/复查时间的排序和筛选。
- 切换视图后保留搜索、筛选和排序意图；刷新后保留用户上次使用的视图。
- 看板拖动可改变阶段、写入时间线并显示撤销；键盘或菜单操作提供等价能力。

#### FR-M1-05 申请详情与编辑（P0）

申请详情必须持续显示当前阶段、优先级、下一步/等待状态，并组织概览、流程、资料和时间线。里程碑 1 的“资料”可以为空态占位，但不能丢失导航结构。

验收标准：

- 用户可以编辑公司、岗位、批次、来源、链接、地点、标签、优先级和备注。
- 普通编辑自动保存并显示“保存中”“已保存”或“保存失败”；失败时输入仍保留且可以重试。
- 从 M1 起，长文本未成功保存的内容同时写入固定 origin IndexedDB 的 `EditorRecoveryDraft`；每个编辑器实例使用独立候选和修订号，重新加载时若存在与数据库不同的候选，必须逐份展示并让用户选择恢复或放弃。成功写入数据库后只清除内容与正式版本相同的候选，其他标签页的不同内容继续保留；该机制不使用 Service Worker，也不扩展为离线正式编辑。
- 离开存在未保存字段的页面前必须完成保存或提示用户处理。
- 所有阶段变化、下一步变化和等待状态变化均写入时间线。

#### FR-M1-06 阶段、下一步与等待状态（P0）

产品必须执行第 7.2 和 7.3 节的领域规则。

验收标准：

- 用户能从详情、看板和表格行操作改变阶段，结果一致。
- 进入归档时必须选择合法原因；取消对话框不改变阶段。
- 恢复归档时可以选择任一非归档阶段，界面只把 `archived_from_stage` 预选为建议；用户还可以明确恢复为待补。
- 一条申请不能同时显示有效下一步和等待状态。
- 等待状态只要求一条承载复查日期/时刻的复查事件，等待对象可为空；到达复查时间后进入今日风险队列。完成或移除行动/等待后，只有用户明确选择稍后补充才进入“缺少下一步”。
- 事件结束只能触发可忽略的状态确认建议，不能自动推进申请。

#### FR-M1-07 事件与日程冲突（P0）

用户可以为申请创建面试、测评/笔试、截止和跟进事件，并在统一日程中查看。

验收标准：

- 创建定时事件时开始时间必填、结束时间可选，并明确展示时区；有结束时间时验证其不早于开始时间，无结束时间时按时间点保存。
- 新事件按数据模型的时间区间/时间点规则检测冲突，命中时展示冲突对象和时间，但用户确认后仍可保存。
- 事件改期、取消和完成均保留历史；取消事件不等同于删除。
- 事件变化不会自动改变申请主阶段。
- M1 面试事件直接关联申请，不依赖尚未实现的面试轮次；M2 建立轮次后可由用户把事件归入具体轮次。

#### FR-M1-08 “今日”首页（P0）

首页按固定优先顺序呈现：逾期与冲突、今天、未来 7 天、等待复查、缺少下一步。

验收标准：

- 同一实体可以在适用的风险摘要中被计数，但列表中必须避免让用户误以为是两条不同记录。
- 每项直接显示时间、公司/岗位或招聘会、事件类型以及可执行的主操作。
- 完成、改期、打开申请、设置下一步等高频操作无需进入超过一层深的页面。
- 没有事项时展示明确的“目前没有需要处理的事项”，并提供创建申请或查看全部申请入口。

#### FR-M1-09 基础日历（P0）

桌面提供月历与日程列表，窄屏默认日程列表。

验收标准：

- 所有业务事件在月历和日程列表中使用同一数据源，修改后两处同步。
- 事件类型不能只靠颜色区分，必须同时有文本或图标。
- 点击日期可以创建该日期的事件；点击事件可以查看上下文和编辑。
- 月历在窄屏不强行压缩，自动切换为日程列表。

#### FR-M1-10 ICS 系统日历导出（P0）

应用关闭后，由系统日历承担可靠提醒。因此 M1 必须支持将事件单向导出为 ICS，不能把该能力推迟到增强里程碑。

验收标准：

- 事件详情可以导出单个事件；日历页可以导出当前筛选结果或全部未来事件。
- 每个业务事件使用稳定 UID、正确时区和合法的开始/结束语义；再次导出同一事件不得无故改变 UID。
- 导出前预览标题、时间、地点、链接、描述和提醒；默认描述不包含普通备注或其他敏感正文。
- 界面明确说明这是单向导出，系统日历中的修改不会回写产品；导出成功后提供打开文件所在位置。
- M1 至少支持面试、测评/笔试、投递截止和跟进/复查；M2 新增招聘会后自动纳入同一导出能力。

#### FR-M1-11 时间线与完整备份 v1（P0）

申请详情必须显示可追溯时间线；产品必须从 M1 直接实现完整备份 v1，不另造临时备份格式。

验收标准：

- 时间线按时间倒序显示，至少覆盖创建、阶段变化、下一步/等待变化、事件结果和撤销。
- 用户不能直接编辑审计型时间线条目；业务修改通过新的时间线条目反映。
- M1 备份必须遵守完整备份 v1 的 manifest、JSON、校验和 ZIP 契约；尚未启用的 M2/M3 表仍以空数组输出，附件目录和计数在无附件时保持合法空值。
- `restore.cmd` 可以在服务停止状态下预检并恢复 v1 备份；演练后业务数据、关联和格式版本一致。
- 备份失败不得破坏当前数据库或覆盖上一份有效备份。

### 8.2 里程碑 2：资料、招聘会与数据安全

#### FR-M2-01 资料库与富文本（P0）

用户可以创建 JD 快照、外部资料和个人面试记录，并从全局资料库或关联详情访问。

验收标准：

- 每条资料必须有类型和至少一个有效业务关联。
- JD 快照正文必填；外部资料标题必填且来源 URL/正文至少一项；个人面试记录正文必填并关联具体面试轮次。一般 JD 或外部资料不强制关联轮次。
- 富文本支持标题、列表、引用、链接、代码和基础强调，并可导出语义等价的 Markdown。
- 长文本具有本地临时草稿；刷新、浏览器崩溃模拟或保存失败后可以恢复。
- 全局资料库可按类型、公司、岗位、标签和更新时间筛选。

#### FR-M2-02 图片与 PDF 附件（P0）

资料可以关联图片或 PDF；面试轮次只能通过关联该轮次的个人面试记录间接拥有附件。

验收标准：

- 产品同时检查扩展名、MIME 和内容签名，拒绝不支持或伪装类型。
- 文件复制到用户附件目录后才算上传成功；移动或删除原文件不影响产品内附件。
- 删除资料时明确说明附件是否随实体进入回收站；永久删除后清理无其他引用的附件。
- 备份与恢复覆盖所有附件并验证 SHA-256。

#### FR-M2-03 面试轮次（P0）

申请内可以创建任意数量、自由命名的面试轮次。

验收标准：

- 每轮可记录类型、顺序、时间、地点/会议链接、面试官、结果和复盘。
- 用户可以关联现有事件或创建新事件；不得产生两个不可识别的重复提醒。
- M1 已直接关联申请的面试事件可以由用户归入轮次，也可以继续作为申请级历史事件；迁移不得猜测轮次或复制事件。
- 取消轮次时关联事件默认保留，并提示用户可选“同时取消事件”；默认选项不得改变事件状态。
- 软删除轮次时，默认在同一事务把该轮次唯一的 `INTERVIEW` 事件降级为直接关联所属申请并保留提醒、稳定标识与历史；确认页也提供“事件一同移入回收站”的显式选项。
- 修改轮次结果只写入时间线并给出阶段建议，不自动推进或归档。
- 个人复盘默认不会进入分享导出。

#### FR-M2-04 招聘会（P0）

提供“即将参加”和“已经参加”的招聘会列表与详情。

验收标准：

- 招聘会详情包含时间、地点、链接、目标公司、目标岗位、现场笔记和会后行动。
- 每个目标岗位的现场状态使用“未接触 / 已接触 / 需跟进 / 不再考虑”，分别对应 `NOT_CONTACTED / CONTACTED / FOLLOW_UP_NEEDED / NOT_INTERESTED`。
- 从目标岗位创建申请时自动带入公司、岗位、招聘会来源和关联；仍执行重复申请警告。
- 招聘会出现在今日和日历中，且冲突规则与其他事件一致。
- 结束后未填写会后行动的招聘会可以进入待处理提示，但不自动创建岗位申请。

#### FR-M2-05 全局搜索与筛选（P0）

用户可以搜索申请、公司、JD、外部资料、个人记录和招聘会。

验收标准：

- 搜索支持中文关键词，并展示命中类型、上下文摘要和所属申请。
- 申请列表支持阶段、优先级、来源、标签和日期范围组合筛选。
- 回收站内容默认不进入结果；用户必须显式进入回收站搜索。
- 搜索无结果时显示当前筛选条件、清除筛选入口和创建入口。

#### FR-M2-06 CSV/Excel 导入与 CSV 导出（P0）

实现必须遵守 [导入、导出与备份协议](IMPORT_EXPORT_SPEC.md)。

验收标准：

- 导入严格经过文件选择、列映射、逐行预览、错误/重复提示和最终确认，预览前不得写入正式数据。
- 确认导入在单个事务中完成；不可恢复错误整体回滚，并保留可下载或可复制的错误报告。
- 导出支持当前筛选与全部申请两个范围，并防止电子表格公式注入。
- 只生成 CSV 导出；支持读取 CSV/XLSX 不代表提供 XLSX 导出。
- 导入后缺少下一步/等待状态的活跃申请进入今日待补队列。

#### FR-M2-07 完整备份、自动备份与恢复（P0）

产品在 M1 完整备份 v1 契约上增加资料与附件内容、每日轮换、可选密码加密，以及通过候选数据 generation 与单一活动指针完成的一致恢复；不得另起不兼容格式。

验收标准：

- 完整包包含清单、JSON 数据、校验值和全部附件；格式及恢复流程符合导入导出协议。
- 自动备份每日最多创建一份，默认保留最近 14 份；保留策略可在设置中查看和修改。
- 手动导出前提示包含敏感数据；用户可以选择符合安全协议的密码加密，不使用 ZipCrypto。
- 用户最终确认后先阻止新请求、优雅停止服务并取得排他维护锁，再为此刻的当前 generation 创建并校验 `pre-restore` 快照；随后在新的数据 generation 中完成恢复、迁移和一致性校验，由维护程序原子替换唯一活动指针。持久化切换日志确保中断后可以验证候选或自动回到完整旧 release-generation 对。

#### FR-M2-08 归档与回收站（P0）

已结束申请进入归档；删除的实体进入保留 30 天的回收站。

验收标准：

- 主看板默认排除归档申请；归档页面可按原因、日期和公司筛选并用于复盘统计。
- 回收站显示剩余保留时间、删除来源和受影响关联。
- 恢复后关联、时间线和附件保持一致；同名或重复冲突时必须提示用户选择合并到现有记录，或采用预填的建议后缀重命名后恢复。不得静默选择，也不得让恢复被重复名称永久阻断。
- 永久删除使用对象名称确认或等强度二次确认，完成后给出不可恢复结果。

#### FR-M2-09 更新前保护（P0）

代码更新和数据库迁移不能以用户数据为试错代价。

验收标准：

- `update.cmd` 在拉取或切换版本前创建可验证备份，并在迁移失败时停止启动新版本。
- 数据库迁移具有版本号、前向测试和失败回滚路径。
- 候选代码使用版本化 release 构建，候选迁移只作用于数据 generation 副本；只有 release 与 generation 联合健康检查通过后才替换活动指针，失败时自动重新启动旧组合。
- Git 更新不读取、覆盖或删除仓库外用户数据，除非执行经过验证的显式迁移。
- 失败界面说明当前数据是否安全、备份位置和恢复步骤。

### 8.3 里程碑 3：增强体验

#### FR-M3-01 PWA、离线草稿与浏览器通知（P1）

应用可以安装为 Windows PWA，并在短暂断连或本地服务重启期间以 `OfflineCaptureDraft` 保护快速创建内容；它不同于 M1 的长文本 `EditorRecoveryDraft` 和 SQLite `CaptureDraft`。

验收标准：

- PWA 在受支持的 Windows 浏览器中可安装，名称、图标和启动地址正确。
- PWA 固定使用 `http://127.0.0.1:3210`；该端口被非本应用进程占用时启动失败并给出处理指引，不静默改用新 origin。
- 离线能力只承诺查看最近缓存的非敏感壳层和保存快速草稿，不承诺离线编辑正式数据库。
- 恢复连接后草稿由用户确认再写入；冲突时不得静默覆盖。
- `OfflineCaptureDraft` 只存在于该固定 origin 的 IndexedDB，不进入完整备份；设置页可查看数量、逐条处理或全部清空。它不得覆盖或冒充 `EditorRecoveryDraft`。
- 浏览器通知需要用户主动授权；拒绝后核心功能完整，设置中可查看状态和重新指引。

#### FR-M3-02 粘贴解析与可选 AI（P1）

用户可以粘贴 JD、招聘通知正文或链接文本生成待确认草稿。无 AI 配置时使用基础规则提取；配置后可以显式调用兼容接口。仅粘贴 URL 时只保存 URL 并解析其文本结构，不自动抓取远程网页正文。

验收标准：

- 基础规则至少尝试提取公司、岗位、时间、地点、链接和事件类型，无法判断的字段保持为空。
- 首版不跟随粘贴链接下载网页；需要解析的正文必须由用户粘贴或明确选择发送给已配置的 AI 接口。
- AI 结果始终标记为草稿，用户确认前不得写入正式实体或改变现有数据。
- 设置支持接口地址、模型名和 API Key；Key 使用 Windows 凭据管理器保存，未配置时隐藏或禁用 AI 操作并说明基础解析仍可用。
- 只有用户明确选择并触发的内容可以发送到外部接口；发送前展示范围，响应和密钥不得写入普通日志。

#### FR-M3-03 脱敏本地分享（P1）

用户可以从记录中选择内容并生成自包含 HTML 或 Markdown 文件，需要 PDF 时使用浏览器打印。

验收标准：

- 生成前必须逐项预览将包含的字段；默认排除申请进度、联系方式、面试官、私人备注、个人复盘和本地文件路径。
- 输出对 HTML 和 Markdown 内容进行转义或净化，不包含可执行脚本和远程跟踪资源。
- 分享文件生成在用户选择的位置，不启动临时公网服务。
- 分享动作和所选字段可在本地时间线中记录，但不得保存分享接收人信息。

#### FR-M3-04 基础统计（P1）

统计位于次要页面，不占据今日首页主位置。

验收标准：

- 提供各阶段数量、基础漏斗、来源结果和按周/月的时间趋势。
- 默认排除示例数据和回收站数据；归档数据按归档原因进入统计。
- 每个图表同时提供文本摘要或数据表，不能只用颜色表达。
- 明确说明数据为历史描述，不提供成功率预测或岗位推荐。

#### FR-M3-05 主题与国际化准备（P1）

界面支持浅色、深色和跟随系统；首版文案为简体中文，代码结构预留国际化资源。

验收标准：

- 三种主题在刷新后保持选择，关键页面均达到无障碍对比度要求。
- 状态、优先级和错误不能只依赖颜色表达。
- 用户可见字符串集中管理，业务数据不存储翻译后的枚举显示名。
- 首版不要求提供英文翻译，也不得在设置中展示不可用的语言切换。

## 9. 跨功能质量要求

### 9.1 数据一致性

- 所有多实体写操作使用事务，尤其是阶段时间线、导入、删除/恢复和附件登记。
- 日期和时刻按数据模型保存时区语义；界面默认使用当前系统时区并明确显示跨日或全天事件。
- 任何迁移、导入或恢复都必须在完成后运行领域一致性检查，包括孤立关联、缺失附件、非法阶段和下一步/等待冲突。

### 9.2 性能基线

在参考数据集（1,000 条申请、5,000 条事件、10,000 条资料元数据，不含附件加载时间）下：

- 本地开发外的生产构建中，主要列表首次可交互目标不超过 2 秒。
- 已加载页面内的筛选和排序反馈目标不超过 200 毫秒。
- 自动保存不阻塞继续输入；大附件处理显示可取消进度。

性能目标不得以跳过校验、备份或安全检查为代价。

### 9.3 可用性与无障碍

- 核心流程满足 WCAG 2.2 AA，具体交互要求见 [UX 规格](UX_SPEC.md)。
- 所有主要操作可使用键盘完成；拖放、颜色和鼠标悬停均必须有等价替代。
- 破坏性操作必须明确影响、提供可恢复路径或二次确认。
- 错误信息说明发生了什么、数据是否安全以及下一步怎么做，不能只显示错误码。

### 9.4 隐私与日志

- 不默认加载第三方统计、字体、脚本或远程图片。
- 日志只记录排障所需的技术摘要，必须清理 JD、面经、姓名、联系方式、链接查询参数、附件路径和密钥。
- 用户可以在设置中查看日志目录、备份目录和数据目录，并能打开目录，但不能从界面误把整个数据目录提交到 Git。

## 10. 发布与范围变更

### 10.1 里程碑完成定义

每个里程碑完成必须同时满足：

- 对应 P0 功能和验收标准全部通过。
- 缺陷严重度与需求优先级分开：S0 为数据丢失、安全问题或不可启动，S1 为核心流程不可用且无绕路，S2 为存在可接受绕路的功能问题，S3 为外观或轻微体验问题；发布时 S0、S1 必须均为 0。
- 单元、集成和关键 Playwright 流程测试通过。
- 数据迁移、备份恢复和失败回滚路径经过固定样例验证。
- 文档与实际行为一致，且没有把后续里程碑的占位界面误标为已完成。
- 在当前支持的 Windows 环境完成一次人工冒烟测试。

### 10.2 后续服务端化的触发条件

当前不计划升级为服务端产品。如果未来重新考虑账号、邀请、在线分享或云同步，应视为新的架构阶段：先新增 ADR 和威胁模型，再设计用户隔离、认证、授权、数据迁移与运营成本；不得直接把本地数据库暴露为公网服务。

### 10.3 需求追踪

- 代码变更和测试应引用对应的 `FR-Mx-xx` 编号。
- 改变主阶段、行动模式、删除策略、数据目录或外部发送边界时，必须先更新本文和相关 ADR。
- 导入、导出、备份的字段级细节以 [导入、导出与备份协议](IMPORT_EXPORT_SPEC.md) 为准；若与本文冲突，先修正文档再实现。
