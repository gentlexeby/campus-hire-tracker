# 测试策略

## 1. 质量目标

测试优先保护四件事：用户不会漏掉关键安排；申请状态不会被系统擅自改变；更新、迁移和导入不会破坏数据；敏感内容不会进入不该出现的位置。

质量门槛按风险而非代码行覆盖率决定。覆盖率用于发现盲区，不能替代业务断言。核心领域服务、迁移、导入恢复、安全边界必须覆盖成功、失败和中断路径。

## 2. 测试金字塔

建议自动化用例数量比例约为 65% 单元、25% 集成、10% E2E；不以比例作为硬性 KPI。

| 层级 | 工具与运行位置 | 主要对象 | 必须避免 |
| --- | --- | --- | --- |
| 单元 | Vitest，纯内存 | 状态规则、下一步/等待约束、日期分组、冲突检测、脱敏、路径校验、格式转换 | mock 掉所有真实规则后只测实现细节 |
| 组件 | Vitest + DOM 测试库 | 表单校验、错误/空/加载状态、键盘操作、富文本净化后的渲染 | 大量脆弱快照 |
| 集成 | Vitest + 临时 SQLite/临时目录 | Drizzle 查询、事务、外键、迁移、附件两阶段写入、导入/备份/恢复 | 使用用户真实数据目录 |
| E2E | Playwright + 独立应用实例 | 跨页面核心流程、持久化、下载、浏览器权限、PWA | 依赖用例执行顺序 |
| 运维验收 | Windows 干净用户环境 | clone、脚本、更新、回滚、凭据和目录权限 | 只在开发机上验证 |

每个测试进程必须获得唯一临时数据根目录和端口。例外是固定 PWA origin 套件：它串行占用 `http://127.0.0.1:3210`，并使用专用临时数据根。测试结束只删除该临时根目录；任何测试检测到路径指向真实 `%LOCALAPPDATA%\CampusHireTracker` 时应立即失败。

## 3. 测试环境与确定性

- CI 固定 Node.js 24 LTS 的具体补丁版本，并使用 `npm ci`。
- 单元和集成测试固定系统时间，显式设置时区；日期用例至少覆盖 `Asia/Shanghai`、UTC、跨午夜、闰日和一个有夏令时的 IANA 时区。必须包含夏令时不存在时间与重复时间，并断言最终保存的 UTC instant 和用户选择。
- SQLite 必须启用外键，测试配置与生产配置一致。
- E2E 每个 worker 使用新数据库、附件目录和浏览器上下文。
- PWA、IndexedDB 和通知权限测试必须使用固定 `127.0.0.1:3210` origin；另有用例先占用 3210，验证应用安全失败且不会换端口创建第二个 origin。
- 网络默认阻断或替换为本地假服务；只有标记的契约测试可访问受控端点。
- 文件夹和文件名夹具包含中文、空格、长名称、组合 Unicode、保留字符和大小写差异。
- 所有随机 ID 使用可注入生成器；断言业务不变量，不断言真实随机值。

## 4. 分层测试清单

### 4.1 领域单元测试

- 主阶段只能取固定枚举；事件结束不改变阶段。
- 活跃申请必须有下一步行动，或等待状态与复查日期；归档申请例外。`WAITING` 必须有复查事件/日期，但 `waiting_for` 文本可空，空值不得被前端、导入器或一致性检查误判为非法。
- 相同公司、岗位和批次产生警告而非硬性拒绝。
- 优先级默认为中，阶段默认为机会池。
- 看板移动、撤销、归档和恢复生成正确时间线事实。
- 今日分组优先级：逾期/冲突、今天、未来 7 天、等待复查、缺少下一步。
- 时间区间冲突、相邻不冲突、全天/定时和跨午夜规则；定时事件的结束时间可空，空值是发生在开始时刻的点事件。点与覆盖该时刻的区间冲突、相同时间的两个点冲突，点落在半开区间的结束边界不冲突。
- 分享默认排除私人备注、面试官、内部 ID、本地路径和申请进度。
- CSV 导出公式注入防护覆盖前导空白、BOM、零宽与控制字符；XLSX 仅用于导入，公式及缓存值永不求值/采用，外部关系永不抓取。首版没有 XLSX 导出测试要求。
- ICS 覆盖 UTF-8 的 75-octet 折行、CRLF、TEXT 转义、属性注入、UTC/全天时间、`DTSTAMP`、`SEQUENCE`、`VALARM`、更新与取消文件。稳定 UID 只作为客户端兼容信号，测试不得假定所有客户端去重。
- 文件对象键、路径规范化、MIME/签名和压缩包成员校验；`object_key` 自带规范小写扩展名，按 `stores/<generation>/attachments/<object_key>` 定位且不得再次拼扩展名。

### 4.2 数据库与服务集成测试

- 约束：外键、唯一索引、软删除过滤、事务回滚和并发写冲突。
- 时间线与业务写入同事务；故意在第二步抛错后两者均不落库。
- 自动保存乱序响应不能用旧内容覆盖新内容。
- 附件按“用户数据根 `tmp/uploads/<operation-id>` 写入 → 打开句柄 flush/fsync → 关闭 → 校验 → 生成含规范小写扩展名的完整 `object_key` → no-replace move 到 `stores/<generation>/attachments/<object_key>` → DB 登记”在每个边界注入失败；移动后登记失败只产生等待期孤儿，不能覆盖旧对象。永久删除验证 GC outbox 仅在数据库提交后，按任务内 `generation_id + object_key` 精确定位、不追加扩展名，并幂等执行和失败重试。
- 附件预算覆盖单文件 `50 MiB`、单批 `20` 个、当前受管总量 `2 GiB`、图片解码 `40 MP`、PDF `500` 页的边界值与刚好超限值；拒绝时正式数据库、目标目录和既有文件均不变。
- 删除公司/招聘会/事件时的关联行为与数据模型一致；软删除面试轮次默认把其主 `INTERVIEW` 事件原子降级为直接关联所属申请，提醒/历史保留，用户明确选择“同时删除事件”时才整组软删除。
- 招聘会允许独立的现场笔记和招聘会级 `FOLLOW_UP` 事件；创建、完成、取消、软删除/恢复时上下文、Today 投影和 `follow_up_status` 一致，不能错误套用申请专属约束。
- 搜索不会返回回收站记录，中文和特殊字符查询结果正确。
- 导入确认前零正式写入；任一行致命错误导致整个批次回滚。
- 完整备份验证 `data.json` v1 schema、确定性字节、精确成员集合、普通 ZIP 的信任提示、加密 envelope、格式兼容和 generation 激活；M1 生成的 v1 必须为尚未开放的 M2/M3 表输出规定的空数组，而不是省略成员或改变格式。不得再用“同时原子切换数据库与附件”作为断言。
- 草稿边界分别测试：SQLite `CaptureDraft` 随 generation 进入完整备份；M1 IndexedDB `EditorRecoveryDraft` 与 M3 IndexedDB `OfflineCaptureDraft` 均不进入备份、不随恢复出现，也不与 SQLite 行共享 ID 或双写。
- 单实例锁阻止两个应用同时写同一数据目录。

### 4.3 组件与可访问性测试

- 必填、重复警告、日期歧义、保存失败和冲突确认均可由键盘完成。
- 焦点在对话框打开、校验失败、关闭后回到合理位置。
- 看板必须提供非拖动式阶段修改；屏幕阅读器能读出阶段和优先级文本。
- 保存中、已保存、失败不能只用颜色表达。
- 明暗主题及 200% 缩放下关键操作仍可见；窄屏无横向遮挡关键按钮。
- 空、加载、错误、无搜索结果和数据迁移阻塞状态均有测试。

### 4.4 掉电注入与并发测试

故障注入使用可控 failpoint 和独立子进程强制终止，不能只抛出可被正常清理的异常。对每个持久化协议在“写入前、写入后未 flush、fsync 后、rename/指针替换后、确认记录前后”终止进程，重启后只允许出现文档定义的旧状态或新状态：

- SQLite 业务事务与时间线：不能出现业务行和时间线半提交。
- 附件：只能从数据根 `tmp/uploads` 发布，不能覆盖已有对象；最多留下超过等待期才可回收的孤儿。GC outbox 不能丢失已提交删除，也不能误删仍引用对象；worker 必须能仅凭持久任务中的 generation、完整对象键和哈希定位目标。
- 备份：目标目录只出现完整可验证包；临时/截断包不参与轮换。
- 恢复/更新：候选 `stores/<generation>`、`activation-journal.json` 和单一 `runtime/active.json` 在任一终止点重启，必须启动完整旧 generation 或完整新 generation，不能混搭数据库与附件。
- 加密导出：salt/nonce/header/ciphertext 任一阶段中断只留下不可选择的临时文件，不能发布未认证包。

并发矩阵至少包含：

- 两个标签用同一 `version` 编辑、自动保存乱序、看板拖动与表单保存竞争，验证显式冲突而非最后写入静默覆盖。
- 普通写入与 CSV/XLSX 导入确认、备份附件清单冻结、回收站清理同时发生，验证锁顺序、快照边界和无死锁。
- 两个进程同时启动、恢复与更新互斥、备份与 generation 激活互斥；输家必须安全退出且不修改 active 指针。
- 两个同内容/同目标键附件并发提交，验证 no-replace、唯一引用和孤儿等待策略。

## 5. 关键 E2E 场景

每条场景独立启动，禁止复用上一条的数据库。

### E2E-01：首次使用与核心闭环（M1 阻断）

1. 首次打开，选择创建第一条申请。
2. 只输入公司和岗位并保存，验证默认阶段和优先级。
3. 填写下一步及截止时间，确认今日首页出现。
4. 创建有结束时间的面试区间；再创建无结束时间的点事件，验证点落在区间内时提示冲突且确认后仍可保存、点恰在半开区间结束边界时不提示冲突。
5. 从看板推进阶段，验证时间线；撤销后验证阶段和时间线。
6. 切换到等待状态并设置复查日期，刷新与重启应用后仍一致。
7. 归档并选择原因，验证默认看板隐藏、归档筛选可见且能恢复。
8. 导出含定时、全天、多提醒和长中文/换行/逗号/分号的 ICS；逐字节验证 UTF-8、CRLF、75-octet 折行不截断码点、TEXT 转义、UTC/`VALUE=DATE`、`DTSTAMP`、`SEQUENCE`、`VALARM` 和敏感字段排除。
9. 更新、取消和软删除事件，验证同一 UID、更高 SEQUENCE，以及 PUBLISH 快照与单独 METHOD:CANCEL 文件；注入 CRLF/`BEGIN:VEVENT` 文本不能形成新属性。在受支持系统日历人工导入候选文件，只记录实际客户端的更新/去重行为，不把它当跨客户端保证。
10. 在长文本编辑器输入未保存内容后刷新或强制结束浏览器，重新打开时由 M1 IndexedDB `EditorRecoveryDraft` 提示恢复；两个标签页写入不同内容时必须形成独立候选，任一标签页正式保存或放弃自己的修订都不得清除另一份不同内容。正式保存只清理与数据库内容相同的候选，正常服务断连不能借此冒充离线创建。
11. 在纯 M1 数据集创建完整备份 v1，验证所有固定 `tables` 成员都存在，尚未开放的 M2/M3 表为规定的空数组；IndexedDB `EditorRecoveryDraft` 不在 manifest、`data.json` 或 ZIP 成员中。随后写入一条仅用于辨别时点的申请，停止服务并通过 `restore.cmd` 恢复该备份，确认时点后的申请消失、备份内核心实体/关联/时间线一致、active 指向新 generation，且 previous generation 保留供回退。

### E2E-02：重复申请与人工确认（M1 阻断）

创建相同“公司 + 岗位 + 批次”的第二条申请，验证警告、取消零写入、确认后允许共存；事件结束后验证阶段没有自动变化。

### E2E-03：资料、面试与附件（M2 阻断）

为申请添加 JD、外部链接、两轮面试和个人复盘；上传一张图片与一个 PDF；重启后预览并全局搜索。删除关联事件后确认面试轮次保留且提示清晰；再软删除有主事件的轮次，默认路径必须把事件从 `interview_round_id` 原子降级为直接 `application_id`、保留提醒与历史，恢复轮次不自动抢回事件。另测用户明确选择“轮次与事件一起删除/恢复”的成组路径。

### E2E-04：招聘会转申请（M2 阻断）

创建招聘会，加入多家公司与目标岗位，记录并重新编辑现场笔记，创建招聘会级 `FOLLOW_UP` 事件并验证 Today/完成状态，从两个目标创建申请；验证来源和关联；取消或删除跟进不改变申请，删除招聘会后申请不被删除。

### E2E-05：表格导入（M2 阻断）

选择含中文、重复项、未知阶段、歧义日期、非法 URL、`next_action + review_at` 冲突、`review_at` 有值但缺 `waiting_for`，以及一行缺公司名的 XLSX；完成列映射和逐行修正，验证 action-only → `ACTION`、review-only → `WAITING` 且允许 `waiting_for=NULL`、两者空 → `NEEDS_ACTION`。公式单元格及其缓存值不得执行/采用，外部关系请求计数必须为零；超行列/成员/解压比/耗时预算的工作簿被拒绝。确认前验证数据库不变；模拟提交中错误验证整体回滚；修复后导入并在当前会话整体撤销。

### E2E-06：同名冲突恢复（M2 阻断）

软删除一家公司及一个标签，再创建规范化同名的活动实体。恢复时分别验证“使用建议后缀重命名”和“合并到现有记录”两条路径：都需明确确认、都能完成，不绕过活动名称唯一索引；公司路径完整重挂岗位、申请、招聘会目标和资料关联，标签路径去重申请/资料关联，所有受影响申请时间线与结果摘要准确。取消确认时零写入。

### E2E-07：完整备份与恢复（M2 阻断）

建立跨实体数据、软删除、时间线、非秘密 AI 配置和附件，生成普通 ZIP 与密码加密包，继续修改当前数据，再分别恢复旧备份；核对 v1 schema、ID/关联、软删除、时间线、设置、附件集合与哈希，并确认凭据/IndexedDB/运行历史未导出。错误密码、AAD/header/ciphertext/tag 篡改、KDF 超限和损坏 ZIP 均应拒绝，统一认证错误不泄漏细节且当前 generation 不变。

### E2E-08：离线草稿与升级（M3 阻断）

在固定 `http://127.0.0.1:3210` 安装 PWA，断网创建 IndexedDB `OfflineCaptureDraft`，验证它与 M1 `EditorRecoveryDraft`、SQLite `CaptureDraft` 明确区分且均不双写；恢复网络后预览并确认一次，模拟重复重试不产生两个申请。完整备份/恢复不包含或恢复两类 IndexedDB 草稿。升级 Service Worker 后页面可重新加载。先由其他进程占用 3210 时应用必须报错退出，不得切换端口造成新的 PWA/IndexedDB origin。

### E2E-09：浏览器提醒（M3 阻断）

分别允许和拒绝通知权限；验证拒绝后不再骚扰，应用关闭时不作后台通知承诺，并始终提示可使用 M1 的系统日历导出获得可靠提醒。

### E2E-10：可选 AI（M3 阻断）

无 Key 时使用规则提取；配置测试凭据后检查发送预览、取消零请求、确认后仅生成 SQLite `CaptureDraft`；模拟 401、429、超时、恶意 HTML 和无效 JSON，验证正式实体不变且日志无 Key。

### E2E-11：脱敏分享（M3 阻断）

选择 JD 和一段手动勾选的面经生成 HTML/Markdown；验证预览与文件不含私人备注、面试官、进度、内部 ID、绝对路径、远程追踪资源或脚本。

## 6. 数据库迁移测试

每个迁移 PR 必须附带以下材料：上一发布 schema 的匿名固定数据库、目标 schema 断言、数据量级样例和失败注入点。

自动测试矩阵：

1. 空数据库直接迁移到最新版本。
2. 上一发布版本逐步迁移到最新版本，并核对核心记录数与关系。
3. 至少一个上一主版本备份经恢复后再迁移。
4. 已是最新版本时再次运行，确认无副作用。
5. 数据库版本高于应用支持版本时只读拒绝，不尝试降级。
6. 在每个事务边界注入异常，确认 schema 版本与数据不会处于“半成功”。
7. 磁盘空间不足、数据库锁定、文件只读和进程中断的错误信息可操作。
8. 迁移后运行 `foreign_key_check`、完整性检查和领域不变量查询。
9. 在 `America/New_York` 覆盖 2026-03-08 02:30（不存在）与 2026-11-01 01:30（重复）等边界：前者必须阻塞并要求修正，后者必须让用户选择 offset，往返后保持同一 UTC instant。

迁移测试不得把“能打开数据库”视为成功。至少核对申请阶段、下一步/等待、事件时区、时间线顺序、软删除状态、附件对象键和 schema 版本。

每个受支持旧 release 都必须有完整更新夹具：从旧 release 启动旧 `stores/<generation>` 并写入数据，运行候选更新生成新 generation。构建/迁移/健康检查成功时 active 指针才指向新 generation；在迁移每个 failpoint、指针替换前后和首次健康检查时终止进程，重启恢复逻辑必须选择完整旧或完整新 generation。失败回退后旧 release 仍能打开旧 generation，候选迁移不得原地改坏它。

## 7. 备份与恢复演练

### 7.1 标准演练数据集

固定数据集至少包含：7 个阶段的申请、重复申请、下一步与等待、跨午夜事件、招聘会、两轮面试、中文富文本、外部链接、图片、PDF、回收站记录和一条不应导出的测试凭据标记。

演练前记录：数据库 SHA-256、各实体数量、关键关联数量、附件清单与哈希、schema 版本和备份格式版本。

### 7.2 成功恢复步骤

1. 在隔离数据目录启动指定旧版本并载入标准数据集。
2. 创建普通 ZIP 与密码加密包；校验 manifest、`data.json` schema/确定性编码、精确成员集合、成员哈希和附件数量。
3. 对当前数据作可观察修改，证明恢复不是读取原数据。
4. 使用目标版本预览恢复，确认替换范围和版本迁移说明。
5. 执行恢复，确认候选位于新的 `stores/<generation>`，服务停止时仅更新 `runtime/active.json`，应用重启并运行数据库完整性与领域一致性检查；应用无法启动的演练必须从固定 `restore.cmd` 进入，`setup.cmd --repair` 只输出诊断且不切换 generation。
6. 核对实体、关系、软删除、时间线、附件哈希与可预览性。
7. 新建并编辑一条记录，证明恢复后的数据库可继续写入。

### 7.3 失败恢复步骤

分别构造：manifest 缺失、data schema 错误、成员哈希错误、附件缺失/额外、未知新格式、`../` 成员、绝对路径、符号链接、超大解压比、临时目录空间不足；加密包另覆盖错误密码、header/AAD/ciphertext/tag 篡改、截断、salt/nonce 长度和恶意 Argon2 参数。

在 generation 构建、journal `PREPARED`、active 临时文件 flush、active 单文件替换和首次健康检查处逐点注入终止。每次均验证：恢复被拒绝或按 journal 明确完成；active 只指向完整旧/新 generation，数据库与附件不会混搭；恢复前快照仍存在；日志只包含错误类别与关联 ID，不包含资料内容、密码或完整用户路径。

发布候选必须有一份人工演练记录，写明版本、时间、操作者、样例版本、结果和发现的问题；不能只引用自动测试结果。

## 8. Windows 全新 clone 验证

至少在 Windows 11 普通用户账户执行；若 README 声称支持 Windows 10，则同样执行一次。测试机不得预装项目依赖，不得使用开发者已有的用户数据。

### 8.1 首次安装

1. 安装受支持的 Git 和 Node.js 24 LTS，确认无需管理员运行应用。
2. 从 GitHub 私有仓库克隆到包含中文和空格的路径。
3. 检查仓库内不存在数据库、附件、备份、日志、`.env` 或真实资料。
4. 双击 `setup.cmd`；验证前置条件提示、`npm ci`、构建、目录初始化和迁移成功。
5. 双击 `start.cmd`；验证只监听 `127.0.0.1:3210`，浏览器用完全相同 origin 打开健康页面；IPv6 和局域网连接失败。关闭拥有服务的命令窗口后，Node Server、worker 和端口均停止，数据库/进程锁释放，且不存在 Windows 服务、托盘或脱离控制台的后台进程；随后可正常重启。
6. 建立核心样例、关闭并重启，确认数据保持；M2 及以后还要上传图片和 PDF 并核对附件。
7. 检查数据实际位于 `%LOCALAPPDATA%\CampusHireTracker`，而非仓库。
8. 导出一个近期事件到系统日历，核对时间与提醒；该步骤从 M1 起执行。
9. 由无关进程占用 3210 后再次启动，验证脚本明确失败、不杀死占用进程，也不自动换端口。
10. 人为制造无法正常启动但备份可读的状态：`setup.cmd --repair` 只诊断并引导；`restore.cmd` 能独立预检、构建新 generation 并按 journal 完成恢复，密码不出现在命令行或日志。

### 8.2 更新成功路径

1. 从上一发布标签安装并建立样例数据。
2. 运行 `update.cmd` 更新到候选版本。
3. 验证更新前备份存在、候选新 generation 完整、active 指向改变、迁移成功、样例和附件完整，旧 generation 仍保留。
4. 重启两次，验证 journal 已收敛且迁移不会重复破坏数据。

### 8.3 更新失败路径

依次模拟依赖安装失败、构建失败、数据库锁定、迁移失败、active 指针替换时终止和健康检查失败。每次验证：脚本退出码非零；journal 恢复后 active 指向完整可用 generation；旧数据库与附件未被候选原地修改；候选库中未完成 GC 作业已重绑定 candidate generation、遗留 `PROCESSING` 租约已安全重置，且不会删除 previous generation 对象；失败产物没有覆盖最后一份可用备份；提示包含旧提交、候选提交、旧/候选 generation 和安全的人工代码恢复办法。脚本不得以强制 Git 重置伪造自动成功回滚。

### 8.4 Git 使用保护

- 在仓库制造已跟踪修改和未跟踪源文件，验证 `update.cmd` 拒绝更新且不自动删除。
- 验证数据目录不受 `git pull`、重新克隆和删除仓库副本影响。
- 验证 Issue 诊断包不包含真实数据或敏感路径。

## 9. 安全与隐私测试

- 监听检查：只允许 IPv4 `127.0.0.1:3210`；IPv6、`0.0.0.0` 和局域网其他设备连接必须失败；端口占用时不得漂移 origin。
- 请求边界：伪造 Host、Origin、CSRF、方法、Content-Type 和超大请求。
- XSS 语料：脚本标签、事件属性、`javascript:` URL、SVG、CSS URL、富文本粘贴和 Markdown 链接。
- 文件输入：双扩展名、伪 MIME、畸形 PDF、NTFS 特殊路径、符号链接/联接点，以及单文件 `50 MiB`、单批 `20` 个、总量 `2 GiB`、图片 `40 MP`、PDF `500` 页各预算的边界/超限；断言暂存只出现在用户数据根 `tmp/uploads`，目标精确使用自带扩展名的 `object_key`。
- 压缩包：Zip Slip、反斜杠/重复规范化成员、大小溢出、极端压缩比、普通 ZIP checksum 协调篡改的信任提示，以及加密 envelope 降级/篡改。
- SSRF：为 AI endpoint 枚举 DNS 多 A/AAAA、DNS rebinding、IPv4/IPv6 私网、loopback、link-local、IPv4-mapped IPv6、metadata 地址/主机名和代理绕过；重定向默认被拒绝，若测试未来逐跳模式则每跳重验，且跨 origin 的接收端永远看不到 `Authorization`。
- 凭据泄漏：在 Key 中放唯一金丝雀值，扫描数据库、日志、备份、导出、错误页面和测试截图。
- CSV 导出：公式标记前有空白、控制字符、BOM 或零宽字符时仍被中和。XLSX 导入：不求值公式或缓存值、不抓外链，并执行成员、解压、行列、单元格与时间预算；首版不测试 XLSX 导出。
- 权限：普通用户可运行；其他 Windows 用户不能因应用自行放宽 ACL 而获得访问。
- 历史副本：在当前 generation 永久删除金丝雀记录后，界面必须明确显示 previous generation/备份仍可能含副本；整代清理只处理未被 active/journal 引用的已验证旧 generation，并同步失去相应回退入口。

## 10. CI、人工检查与发布规则

PR 必须运行：

```text
npm ci
npm run typecheck
npm run lint
npm test
npm run build
```

影响核心流程、持久化、导入导出或浏览器行为的 PR 还必须运行对应 Playwright 项目。定时任务运行完整 E2E、安全语料、依赖审计和备份恢复矩阵；发布标签运行 Windows 全新 clone 验证。

发布阻断：

- 任一 `S0`/`S1` 缺陷、核心 E2E 失败、迁移/恢复失败或凭据泄漏。此处是缺陷严重度（不是安全文档的数据敏感等级）；定义与处置时限以 [实施计划](IMPLEMENTATION_PLAN.md) 的统一缺陷分级为准，测试文档不另造一套等级。
- 新增迁移没有旧版本夹具或失败注入测试。
- 测试存在未说明的偶发失败；禁止通过盲目重试掩盖。
- 覆盖率相对主分支显著下降且触及高风险模块。

偶发测试必须立即隔离并建立缺陷，记录首次出现版本、环境和最小复现；隔离不等于删除发布门禁，核心流程不得以“flaky”为由跳过。

## 11. 测试数据与证据管理

- 只提交合成公司、岗位、面经、邮箱、文件和 API Key；真实求职数据不得进入仓库、CI 或截图。
